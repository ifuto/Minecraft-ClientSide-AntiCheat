# 脅威モデルと数学的考察 - クライアントサイドアンチチート

## 1. 目的

本アンチチートは4層構造で設計されている：

1. **パッケージハッシュ検査**：既知チートのJavaパッケージをSHA-256截断ハッシュで検出
2. **Modsフォルダ監視 (DLL)**：バックグラウンドでModsフォルダを監視し、既知チートjarファイル名を検出
3. **メモリ監視 (DLL)**：プロセスモジュール列挙、RWX領域検出
4. **入力真正性検証**：ハードウェア入力 vs Mod生成入力の判別、回転・CPS解析

検出時、クライアントは **自己BANパケット** `anticheat:violation` をサーバへ送信し、サーバプラグインが `minecraft:ban` を実行。

## 2. 矛盾の指摘 (Core Contradiction)

### 2.1 信頼のパラドックス (Self-Reporting Trust Paradox)

**矛盾**：チートを使用しているクライアント自身に「自分をBANするようサーバへ報告せよ」と求めるのは、信頼モデルとして根本的に矛盾する。

形式的記述：

- クライアント C がチート状態 T にあるとする
- アンチチート A は C 上で実行され、T を検出したときBAN要求パケット P を送信すべき
- しかし T を達成できる攻撃者は、A を改変して P の送信を無効化する能力も持つ (A' に改変)
- したがって、P を送信する誠実なクライアントはチートしておらず、チートしているクライアントは P を送信しない ⇒ 検出-報告の対偶が成立しない

**数学的帰結**：

- 攻撃者がAのコードを完全に制御できる場合、検出確率 Pdetection は1であっても、報告確率 Preport = 0 となり、最終的なBAN確率 Pban = Pdetection * Preport = 0
- これは、クライアントサイドアンチチートが **セキュアエンクレーブ (SGX, TPM) などのハードウェア支援遠隔アテステーション** なしでは、理論的に完全な安全性を達成できないことを意味する

**緩和策 (Mitigations)**：
1. **ハートビート要件**：クライアントは30秒ごとに生存パケット(heartbeat)を送信。サーバはheartbeatが途絶えたクライアントを「改ざん疑い」としてKick。攻撃者がheartbeatを偽造し続ける必要があり、難易度を上げる
2. **Jarハッシュチャレンジ**：サーバがランダムnonceを送信、クライアントは自身のjarのSHA-256とnonceをHMACして返答。攻撃者は正しいjarハッシュを偽造する必要があるが、jarを改変すればハッシュが変わる。ただし、攻撃者は正規jarのハッシュを事前に計算して返答できるため、リプレイ攻撃が可能 → nonceで緩和だが、プロトコル自体を改変すれば再び回避可能
3. **難読化・整合性チェック**：DLLのハッシュを検証し、改変を検出。ただし、検証ロジック自体がクライアント側にあるため、攻撃者は検証をNOPにできる
4. **最終的結論**：本アンチチートは「初心者・中級者のチート利用の抑止」と「ログ収集」には有効だが、**熟練攻撃者による完全なバイパスを防止することは数学的に不可能**。サーバサイドアンチチート (NoCheatPlus, Grim, Vulcan etc) と組み合わせるべき

### 2.2 パッケージ名ハッシュの回避可能性

- ハッシュブラックリストはパッケージ名をそのまま比較するのみ
- 攻撃者はチートを `com.example.myutil` のようにリネームすれば回避可能 (shading / jarjar)
- パッケージ名空間のサイズは無限であり、ブラックリスト方式は **包含関係ではなく列挙** であるため、完全性は持たない

形式的には：

- 全パッケージ集合 U は可算無限
- ブラックリスト B は有限 (n=71)
- 攻撃者は B' = B の補集合から任意の要素を選べるため、回避確率は (U \ B) / U ≈ 1

**緩和策**：行動ベース検出 (CPS, Rotation, Input Authenticity) で補完。パッケージ名が変えられても、KillAuraの回転スナップは検出される。

### 2.3 ファイル監視の限界

- Modsフォルダのみを監視 → 攻撃者は `-javaagent:/tmp/cheat.jar` や、カスタムクラスローダーでメモリ上からクラスをロードすることで回避可能
- ファイル名は substrings ハッシュで検出するが、攻撃者はファイル名を `a.jar` のように無害な名前にすれば回避可能。ただし、jar内部のパッケージは依然としてパッケージスキャナで検出されるため、2層で補完

### 2.4 メモリ監視の限界

- `EnumProcessModules` はPEBのモジュールリストに依存。Manual Map (手動マッピング) されたDLLはこのリストに乗らないため検出回避可能
- RWX領域の検出：JVMのJITが正当にRWX領域を生成するため、閾値ベースの heuristic は false positive / false negative のトレードオフを持つ

RWX検出の統計：
- 正常JVMでRWX領域数 X はポアソン分布に近い、平均 λ ≈ 5-15
- 閾値を30とすると、正常時に誤検知する確率は P(X>30) = 1 - CDF_Poisson(30; λ=15) ≈ 0.0003 (0.03%) と小さい
- しかし、攻撃者がRWXをRX+RWに分離して注入すれば回避可能

### 2.5 入力真正性検証の限界

- `LLKHF_INJECTED` フラグは `SendInput` API による注入のみを検出。カーネルドライバやHIDデバイス (Arduino) 経由の入力はハードウェアとして見え、フラグが立たない
- したがって、ハードウェアチート (DMA, Arduino mouse) は本手法では検出不可能

統計的検出の限界：
- 人間のCPSのCV (変動係数) は 0.15-0.4
- AutoclickerのCVは 0.01-0.05
- 閾値0.05とすると、人間の低CV jitter clicking (熟練プレイヤー) が誤検知される可能性：熟練者のCVが0.04程度になることもある → 連続5回超過を要求することで誤BAN確率を下げる
- 数学的に：1回の誤検知確率を p=0.02 とすると、5回連続誤検知は p^5 = 3.2e-9 と無視可能

回転のGCDチェック：
- Vanillaの感度GCDは (s*0.6+0.2)^3 * 8.0
- ModがこのGCDを無視して回転を直接設定すると、GCD違反が検出できる
- しかし、賢いチートはGCDを考慮して回転を量子化すれば回避可能

## 3. 各検出の数学的正当性

### 3.1 ハッシュ衝突確率

SHA-256を64bitに截断した場合、n個のエントリでの衝突確率：

P_collision ≈ 1 - exp(-n^2 / 2^{65})

n=71 (Critical packages) のとき：

P ≈ 1 - exp(-71^2 / 2^{65}) ≈ 71^2 / 2^{65} ≈ 5041 / 3.6e19 ≈ 1.4e-16

無視可能。

ファイル名 n=73 でも同様。

したがって、誤検知がハッシュ衝突による確率は現実的にゼロ。

### 3.2 サブストリングハッシュ検出の計算量

ファイル名長 L=30, サブストリング長 [3,30] の全列挙：

Number_substrings = sum_{l=3}^{30} (L-l+1) = O(L^2) ≈ 400

各ハッシュ計算が SHA-256 (~ 数µs) なので、1ファイルあたり ~ 2ms。Modsフォルダイベントは稀なので性能影響なし。

### 3.3 CPS解析の統計的妥当性

Window size W=20, 標本平均 m, 不偏分散 s^2, CV = s/m

人間クリック間隔 I_i ~ Normal(μ, σ^2) + 反射時間

Autoclicker: I_i = μ + ε, ε~Uniform(-δ,δ), δ<<μ → CV小

- 閾値 CV<0.05 は、人間分布の3σ外に相当 (人間CV平均0.2, σ≈0.08 → 0.05は -1.875σ, 片側確率 ≈3%)
- 単発では誤検知3%あるが、連続3回要求で 0.03^3 = 2.7e-5 (0.0027%) に低下

### 3.4 回転スナップ検出

1tick=50ms, 最大人間yaw速度 ω_max ≈ 60deg/tick (設定値)

KillAuraのsnapはしばしば 180deg in 1 tick → ω=180 > ω_max で検出

人間が180度振り向くのに必要な時間：通常 200-400ms (4-8 ticks) → 1 tickで180度は生理的に不可能 (マウスを非常に速く動かしても、OSの加速度とMinecraftの処理で分散される)

したがって、閾値60deg/tickは保守的だが安全。

## 4. 誤検知を避けるための除外リスト

以下のModは正当だが、初期リストに含まれていたり、ブラックリストに近いため **除外** した：

- **Sodium, Lithium, Iris, FerriteCore** 等パフォーマンスMod：チートではない
- **OptiFine**: 正当な最適化Mod, パッケージ `net.optifine` → 除外
- **Lunar Client / Badlion Client**: 正当ランチャー、チート要素なし → `com.moonsworth.lunar`, `net.badlion` 除外
- **Xaero Map, Journeymap, VoxelMap**: ミニマップは一部サーバでは許可、厳密なチートではないため SUSPICIOUS に格下げ or 除外 (本実装では SUSPICIOUS)
- **Tweakeroo, MaLiLib, Litematica**: ユーティリティMod、EasyPlace以外はチートではない → SUSPICIOUS or 除外
- **Malilib**: Litematica等のライブラリ → 誤検知を避けるため除外
- **Zoomify**: ズームはVanilla 1.20で公式機能化 → 除外
- **NoChatReports**: プライバシーMod、Wurstに同梱されるが自体はチートではない → 除外
- **ViaVersion, ViaFabricPlus**: バージョン偽装に使われる可能性あるが、正規の互換Mod → 除外
- **PacketEvents, ByteBuddy, Javassist, Guava EventBus, Forge EventBus**: 汎用ライブラリ → 除外 (チートが使うが正当Modも使う)

これにより、誤BANリスクを下げている。

## 5. 自己BANパケットのプロトコル

### 5.1 フォーマット

```json
{
  "v":1,
  "playerUuid":"...",
  "playerName":"...",
  "type":"PACKAGE",
  "subType":"CRITICAL",
  "detail":"meteordevelopment.meteorclient",
  "ts":1710000000,
  "nonce":"a1b2c3d4",
  "sig":"hmac-sha256 hex"
}
```

HMAC: `HMAC-SHA256(secret, uuid|type|subType|detail|ts|nonce)`

### 5.2 サーバ側検証

- `player` オブジェクトは Bukkit が保証 (パケットを送信した接続から取得)
- `playerUuid` はクライアントが主張するUUIDだが、サーバは接続のUUIDと比較可能 (今回は簡易的に信頼)
- HMAC検証により、第三者が他プレイヤーをBANさせる偽パケットを防ぐ
- ただし、secretはクライアントに存在するため、抽出されれば偽造可能 → 根本的限界は 2.1 に同じ

### 5.3 BAN実行

`Bukkit.dispatchCommand(console, "ban %player% %reason%")` で実行。Vanillaの `minecraft:ban` と互換、LiteBans等のプラグインでも動作。

## 6. 追加アイデア (実装済み+提案)

### 実装済み

- **Rotation Analyzer**: GCDチェック、Snap検出
- **CPS Analyzer**: CVベースのAutoclicker検出
- **Heartbeat**: 改ざん検出
- **Jarハッシュ**: Attestation

### 提案 (今後の拡張)

- **Movement Analyzer**: Timer, Fly, Speedの検出 (クライアント側でプレイヤー移動速度を監視し、サーバの想定と乖離したらフラグ)
- **OpenGL Hook検出**: 外部オーバーレイ (チートGUI) がOpenGLコンテキストにフックしているか検出
- **ClassLoader検証**: `ClassLoader` が `KnotClassLoader` 以外なら改ざん疑い
- **Mixin Config検証**: 想定外のMixinがロードされていないかチェック
- **Screenshot検証**: クライアント画面を定期的にキャプチャし、サーバへ送信して人手 or AIでチートGUIを検出 (プライバシー懸念大)
- **Secure Enclave**: Intel SGXやTPMを用いた遠隔アテステーション (将来的な理想解)

## 7. 結論

本アンチチートは、**クライアントが協力的であるという前提** では高い検出率を持つが、**非協力的な攻撃者に対しては理論的に完全ではない**。これはクライアントサイドアンチチートの根本的限界であり、数学的に証明可能 (信頼のパラドックス)。

したがって、本Modは：

- **抑止力**として (初心者が簡単にチートを使えなくする)
- **サーバサイドアンチチートの補助**として (クライアントの自己申告でBanを高速化)
- **コミュニティサーバのポリシー執行**として (Mod導入を義務化し、導入していない者はKick)

として運用すべきであり、単独で万能な解決策とはならない。

サーバ管理者には、必ずサーバサイドのアンチチート (GrimAC, Vulcan, NoCheatPlus) と併用することを推奨する。
